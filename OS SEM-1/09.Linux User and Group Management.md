## 1. Introduction and How to Use These Commands

This is a reference guide for system administrators covering **user account creation, group structure, authentication configuration files, and practical security scenarios**.

> **Note (from the PDF):** Depending on your Linux distribution and configuration, system administration commands can be run using `sudo` or directly as the `root` user. If you are already logged in as root, `sudo` is not required.

📌 **Supplement — safety warning:** All commands in this guide modify system-critical files (`/etc/passwd`, `/etc/shadow`, `/etc/group`). Mistakes can lock users (or you) out of the system. Prefer the dedicated tools (`useradd`, `usermod`, `gpasswd`, `vipw`, `vigr`) over manual file editing. *(Source: [shadow-utils tools, man7](https://man7.org/linux/man-pages/man8/useradd.8.html))*

## 2. Fundamental Concepts

### 2.1 Simple Definition

Linux is a **multi-user operating system** designed to **isolate resources, manage system access, and enforce security policies**. Every process and every file on a Linux system is associated with a **specific user and group**.

> **Why this matters:** Because *everything* belongs to someone, access control becomes a simple, universal question for any action: "Does this user/group have permission?" This is the foundation of Linux security.

### 2.2 Account Types

*(Overlaps with file `01` §2 — repeated here for completeness, since exams test this directly.)*

| Account Type | UID Range | Purpose | Key Characteristics |
|---|---|---|---|
| **Superuser (root)** | `0` | Unrestricted permissions across the entire system | Can do anything; the "administrator" identity |
| **System Accounts** | `1–999` | Created automatically by the OS or software packages to run services (e.g., `www-data`, `nginx`, `postgres`) | Usually **no interactive login shells** |
| **Regular Accounts** | `1000+` (modern distributions) | Assigned to **human users** for interactive sessions | Home directory, login shell, limited privileges |

**Internal working (why system accounts exist):** A compromised web server running as `www-data` only damages what `www-data` can access — not the whole system. This is the **principle of least privilege** applied automatically by package installers.

### 2.3 Groups

**Groups are logical collections of accounts** used to **assign permissions to multiple users simultaneously**.

| Group Type | Assigned When | Effect |
|---|---|---|
| **Primary Group** | Assigned to a user **upon creation** | Files created by the user are owned by their **primary group by default** |
| **Secondary (Supplementary) Groups** | Optional, added later | Grant **additional privileges** — e.g., access to shared folders or specific system software (e.g., `docker`, `sudo`, `wheel`) |

**Diagram — one user, multiple groups:**

```
                 ┌───────────────────────────┐
                 │        User: jerry        │
                 └───────────────────────────┘
                       │              │
             PRIMARY (1 only)   SECONDARY (many)
                       │              │
                ┌──────┴───┐   ┌──────┼────────┐
                │ jerry    │   │ docker│ sudo  │
                │ (GID 1050)│  │      │       │
                └──────────┘   └──────┴───────┘
                New files →           Extra access →
                owned by "jerry"      docker cmds, sudo rights
                group
```

**Exam relevance:** "A user has exactly **one** primary group and **zero or many** secondary groups" is a standard exam distinction.

## 3. Core Configuration Files

### 3.1 Overview Table (from the PDF)

| File Path | Description | Access Permissions |
|---|---|---|
| `/etc/passwd` | Contains user account information (username, UID, GID, home dir, shell). | **Read-all (644)** |
| `/etc/shadow` | Encrypted passwords and account expiration details. | **Root only (600 or 640)** |
| `/etc/group` | Defines group names, Group IDs (GIDs), and list of members. | **Read-all (644)** |
| `/etc/gshadow` | **Group password details and administrative group overrides.** | **Root only (600 or 640)** |

> 📌 **Supplement:** `/etc/gshadow` is the *secure counterpart* of `/etc/group` — exactly as `/etc/shadow` is to `/etc/passwd`. It holds encrypted group passwords and the list of **group administrators** (set by `gpasswd -A`, see §5.3). *(Source: [gshadow(5)](https://man7.org/linux/man-pages/man5/gshadow.5.html))*

### 3.2 Why the Split Between "Readable" and "Root-Only" Files?

- **World-readable files** (`passwd`, `group`) are needed by ordinary programs just to *translate* UID 1001 → "jerry" — they contain no secrets.
- **Root-only files** (`shadow`, `gshadow`) contain **hashes**; making them readable would let attackers run offline brute-force cracking.

*(Deep field-by-field breakdowns of `/etc/passwd`, `/etc/shadow`, and `/etc/group` are in `01.Linux_Access_Control_Users_and_Permissions.md` §5.)*

### 3.3 `/etc/passwd` Field Structure (from the PDF)

```
devuser:x:1001:1001:Developer Account:/home/devuser:/bin/bash
```

| # | Field | Value | Meaning |
|---|---|---|---|
| 1 | **Username** | `devuser` | Login name |
| 2 | **Password Placeholder** | `x` | Indicates password is encrypted in `/etc/shadow` |
| 3 | **UID** | `1001` | User ID (regular account range) |
| 4 | **GID** | `1001` | **Primary Group** ID |
| 5 | **GECOS** | `Developer Account` | User comments/metadata |
| 6 | **Home Directory** | `/home/devuser` | User's personal directory |
| 7 | **Default Shell** | `/bin/bash` | Command interpreter at login |

## 4. Managing Users

### 4.1 Creating User Accounts — `useradd` vs. `adduser`

From the PDF:
- **`useradd`** is a **low-level utility** used to create user accounts (available on all distributions; precise, scriptable).
- **`adduser`** is a **friendly interactive Perl script available on Debian/Ubuntu systems** (asks you questions step by step).

> 📌 **Supplement (cited):** On **RHEL/Fedora/CentOS**, `adduser` is typically just a symlink to `useradd` — behavior differs by distribution, a common exam/interview point. *(Source: [useradd(8)](https://man7.org/linux/man-pages/man8/useradd.8.html), Debian adduser docs)*

#### Example 1 — Default user with home directory

```bash
sudo useradd -m tom
```

| Part | Meaning |
|---|---|
| `sudo` | Run with admin privileges |
| `useradd` | Create the account |
| `-m` | **Create the home directory** (`/home/tom`) and copy skeleton files |

⚠️ **Critical tip:** On many distributions, `useradd` **without** `-m` creates the account *without* a home directory — a very common beginner mistake. (Debian's `useradd` defaults differ from RHEL's; be explicit with `-m`.)

#### Example 2 — User with explicit parameters (from the PDF)

```bash
sudo useradd -u 1050 -m -d /opt/developers/jerry -s /bin/zsh -g developers -G docker,sudo jerry
```

| Option | Meaning |
|---|---|
| `-u 1050` | Assign UID **1050** explicitly |
| `-m` | Create home directory |
| `-d /opt/developers/jerry` | Custom **home directory** path |
| `-s /bin/zsh` | Custom **shell** (zsh instead of bash) |
| `-g developers` | **Primary group** = `developers` (must already exist) |
| `-G docker,sudo` | **Secondary groups** (comma-separated, no spaces) |
| `jerry` | Username (always last) |

#### Example 3 — Non-interactive system service account (from the PDF)

```bash
sudo useradd -r -s /usr/sbin/nologin mickey_service
```

| Option | Meaning |
|---|---|
| `-r` | Create a **system account** (UID from the system range; no home aging) |
| `-s /usr/sbin/nologin` | Shell that politely refuses interactive login |

**Why:** Service accounts shouldn't be able to log in — they only need to *run a process*. The `nologin` shell enforces this while still allowing the service to run under that identity.

### 4.2 Modifying User Accounts — `usermod`

Use **`usermod`** to alter existing account parameters.

#### Add user to a supplementary group — with the critical `-aG` flag

```bash
sudo usermod -aG sudo tom
```

| Option | Meaning |
|---|---|
| `-a` (**append**) | Add to the list **without removing existing memberships** |
| `-G sudo` | The supplementary group(s) to modify |

> ⭐ **Most important tip in this section:** `usermod -G sudo tom` **without** `-a` **replaces** *all* of tom's secondary groups with just `sudo`. This is one of the most damaging one-letter mistakes in Linux administration. Always use `-aG` together.

#### Change login name and move the home directory (from the PDF)

```bash
sudo usermod -l tom_new -d /home/tom_new -m tom
```

| Option | Meaning |
|---|---|
| `-l tom_new` | New **login name** |
| `-d /home/tom_new` | New home directory **path** |
| `-m` | **Move** the contents of the old home to the new location |
| `tom` | Current username (last) |

#### Lock and unlock a user account (from the PDF)

```bash
# Lock user account (prepends ! to password in /etc/shadow)
sudo usermod -L tom
# Unlock user account
sudo usermod -U tom
```

**Internal working:** `-L` doesn't delete the password — it puts `!` in front of the hash in `/etc/shadow` (e.g., `!$6$vQ9x...`), so no entered password can ever match. `-U` removes the `!`.

> 📌 **Supplement (cited):** Locking via `!` blocks *password* authentication, but the account may still be reachable via **SSH keys**. For a full lock, also set the shell to `nologin` or use `usermod -L -e 1 tom` (expire the account). *(Source: [usermod(8)](https://man7.org/linux/man-pages/man8/usermod.8.html))*

### 4.3 Managing Passwords and Aging — `passwd` and `chage`

#### Set or change a user's password

```bash
sudo passwd tom
```
Prompts interactively for the new password (typed input is not echoed to the screen).

#### Force password change at next login (from the PDF)

```bash
sudo passwd -e tom
```
`-e` (**expire**) makes the current password immediately expired — the user **must** set a new one at next login.

#### Configure password aging policies (from the PDF)

```bash
sudo chage -M 90 -m 7 -W 14 tom
```

| Option | Field Affected (in `/etc/shadow`) | Meaning |
|---|---|---|
| `-M 90` | Maximum age | Password valid for at most **90 days** |
| `-m 7` | Minimum age | Cannot change again for **7 days** (prevents cycling back to an old password) |
| `-W 14` | Warning period | User is warned **14 days** before expiry |

#### Set account expiration date (from the PDF)

```bash
sudo chage -E 2026-12-31 tom
```
`-E` sets the absolute account expiry in `YYYY-MM-DD` format — after this date the account cannot log in at all.

#### Inspect the policy

```bash
sudo chage -l tom     # -l lists current aging settings (lowercase L)
```

### 4.4 Deleting User Accounts — `userdel`

#### Delete account, keep the home directory (from the PDF)

```bash
sudo userdel tom
```
Removes the account entries from `/etc/passwd` and `/etc/shadow` but **leaves the home directory intact**.

#### Delete account *and* home directory (from the PDF)

```bash
sudo userdel -r tom    # -r = remove home directory and mail spool
```

⚠️ **Warning:** `-r` is **destructive and irreversible** — all personal files are deleted. Also note: files the user owned *elsewhere* on the system become **orphaned** (owned by a raw UID number with no account — see §7 auditing).

> 📌 **Supplement (cited):** `userdel` refuses to delete a user who is currently logged in. *(Source: [userdel(8)](https://man7.org/linux/man-pages/man8/userdel.8.html))*

## 5. Managing Groups

### 5.1 Group Administration Commands

> 🔧 **PDF correction:** The source text reads "Create a new group:**h**" and "Modify group name or GID:**h**" — the trailing "h" characters are typographical artifacts and have been removed below.

#### Create a new group

```bash
sudo groupadd engineering
```

#### Create a *system* group (typically GID < 1000)

```bash
sudo groupadd -r sys_audit
```
`-r` selects a GID from the **system range** — mirroring `useradd -r` for accounts.

#### Modify group name

```bash
sudo groupmod -n devops engineering
```
`-n devops` renames `engineering` → `devops`. Memberships are preserved (they reference the GID, not the name).

#### Modify Group ID

```bash
sudo groupmod -g 2005 devops
```
Changes the GID to `2005`. ⚠️ **Caution (📌 Supplement):** files owned by the *old* GID are **not** automatically re-owned; run `chgrp -R` or `chown -R :devops` on affected trees afterward. *(Source: [groupmod(8)](https://man7.org/linux/man-pages/man8/groupmod.8.html))*

#### Delete a group

```bash
sudo groupdel devops
```
⚠️ **Warning (📌 Supplement):** `groupdel` refuses to remove a user's **primary** group — remove/change the user's primary group first. Group deletion does not fix up files owned by that group. *(Source: [groupdel(8)](https://man7.org/linux/man-pages/man8/groupdel.8.html))*

### 5.2 Command Summary Table

| Task | Command | Key Option |
|---|---|---|
| Create group | `groupadd engineering` | `-r` = system group |
| Rename group | `groupmod -n NEW OLD` | — |
| Change GID | `groupmod -g 2005 devops` | — |
| Delete group | `groupdel devops` | — |
| Add user to group | `usermod -aG GROUP USER` **or** `gpasswd -a USER GROUP` | `-a` = append |
| Remove user from group | `gpasswd -d USER GROUP` | — |
| Assign group admin | `gpasswd -A USER GROUP` | — |

### 5.3 Managing Group Memberships with `gpasswd`

#### Add a user to a group

```bash
sudo gpasswd -a jerry engineering
```
(`-a` = add.)

#### Remove a user from a group

```bash
sudo gpasswd -d jerry engineering
```
(`-d` = delete.)

#### Assign group administrators (from the PDF)

```bash
sudo gpasswd -A tom engineering
```

**What this does:** Makes `tom` a **group administrator** — a user who can **add/remove members without root privileges**. This delegation is recorded in `/etc/gshadow`.

> 📌 **Supplement (cited):** `gpasswd -A "" group` removes group administrators; `-M` sets the full member list at once. *(Source: [gpasswd(1)](https://man7.org/linux/man-pages/man1/gpasswd.1.html))*

**`usermod -aG` vs. `gpasswd -a` — same result, different perspective:**

| Aspect | `usermod -aG group user` | `gpasswd -a user group` |
|---|---|---|
| Perspective | Edits the **user's** group list | Edits the **group's** member list |
| Requires | Root | Root **or** a group administrator (`-A`) |
| Best for | Admin scripting | Delegated team management |

> These three scenarios are the **practical heart** of this PDF — very likely to appear as "solve this scenario" exam/practical questions. Practice them on a VM.

### Scenario 1: Collaborative Shared Directory with SetGID

**Goal:** Create a shared project workspace (`/srv/projects/alpha`) for the `developers` team. Any file created within this directory must **automatically inherit group ownership** of `developers`, allowing all team members full edit access.

#### Step-by-Step Solution (from the PDF)

**Step 1 — Create the project group:**
```bash
sudo groupadd developers
```

**Step 2 — Add user accounts to the group:**
```bash
sudo usermod -aG developers daffy
sudo usermod -aG developers goofy
```
*(Note `-aG` — append, don't replace.)*

**Step 3 — Create the shared directory:**
```bash
sudo mkdir -p /srv/projects/alpha
```
(`-p` creates parent directories as needed.)

**Step 4 — Change group ownership of the directory to `developers`:**
```bash
sudo chgrp -R developers /srv/projects/alpha
```

**Step 5 — Set access permissions:**
- Full permissions (`rwx`) for **owner** and **group**.
- No permissions (`---`) for **others**.
- Enable **SetGID bit (2)** on the directory so new files **inherit the group ownership automatically**.

```bash
sudo chmod -R 2770 /srv/projects/alpha
```

**Step 6 — Verify directory flags:**
```bash
ls -ld /srv/projects/alpha
# Output: drwxrws--- 2 root developers 4096 Sep 24 12:00 /srv/projects/alpha
```

#### Decoding the Result

| Characters | Meaning |
|---|---|
| `d` | Directory |
| `rwx` | Owner (root): full access |
| `rws` | Group: `rwx` **+ SGID** — the `s` replaces `x`, proving the SetGID bit is active |
| `---` | Others: no access |
| `2` | Link count |

**Why SGID is the key ingredient:** Without it, a file created by `daffy` would be group-owned by *daffy's primary group* — so `goofy` couldn't edit it. With SGID, every new file inherits group `developers`. ✔ (Theory: see `01` §10.3.)

> ⚠️ **Practical notes (📌 Supplement):**
> - Existing users must **log out and back in** (or `newgrp developers`) for new group membership to take effect in their running sessions.
> - The PDF applies `chmod -R 2770`; the **SGID bit is what matters on the directory itself** — recursive SGID on files is usually unnecessary (`chmod 2770` on the directory alone is often sufficient and safer).
> - Members also need `umask` to permit group writes (e.g., `umask 002`, or a default ACL) — otherwise their new files may be group-readable but not group-writable. *(Source: [permissions(7)](https://man7.org/linux/man-pages/man7/permissions.7.html))*

### Scenario 2: Strict Departmental Data Isolation

**Goal:** Configure isolated directories for **HR** and **Finance** departments on a central server. Members of HR must **not** be able to read Finance files, and vice versa. Others must have **zero access**.

#### Step-by-Step Solution (from the PDF)

**Step 1 — Create departmental groups:**
```bash
sudo groupadd hr_dept
sudo groupadd fin_dept
```

**Step 2 — Assign staff to their respective groups:**
```bash
sudo usermod -aG hr_dept bugs_bunny
sudo usermod -aG fin_dept porky_pig
```

**Step 3 — Create isolated directories:**
```bash
sudo mkdir -p /data/hr /data/finance
```

**Step 4 — Apply restrictive ownership and permissions:**
```bash
# HR Directory setup
sudo chown -R root:hr_dept /data/hr
sudo chmod 770 /data/hr

# Finance Directory setup
sudo chown -R root:fin_dept /data/finance
sudo chmod 770 /data/finance
```

**Step 5 — Verify security isolation:**
```bash
ls -ld /data/hr /data/finance
# Output:
# drwxrwx--- 2 root hr_dept 4096 Sep 24 12:00 /data/hr
# drwxrwx--- 2 root fin_dept 4096 Sep 24 12:00 /data/finance
```

#### How the Isolation Works — the reasoning chain

1. **Owner** = `root` with `rwx` → only the administrator has complete control.
2. **Group** = department team with `rwx` → members collaborate fully.
3. **Others** = `---` → everyone else (including the *other* department) gets **nothing**.
4. `bugs_bunny` (in `hr_dept`) is *not* in `fin_dept`, so he falls into the "others" category for `/data/finance` → **no access**. ✔

**Contrast with Scenario 1:** Here the permission `770` **without** SGID is enough, because the goal is *isolation* (who can see what), not *shared file creation* (whose group owns new files). Choosing between `770` and `2770` depends on the goal — a classic exam discussion point.

### Scenario 3: Onboarding a Temporary External Auditor

**Goal:** Provide temporary system access to an external auditor (`donald_duck`). The account must:
1. **expire automatically in 30 days**,
2. have **restricted privileges**, and
3. be **forced to update its initial temporary password immediately upon first login**.

#### Step-by-Step Solution (from the PDF)

**Step 1 — Create user account with a standard non-privileged shell and explicit expiry date:**
```bash
sudo useradd -m -s /bin/bash -e 2026-10-24 donald_duck
```
| Option | Meaning |
|---|---|
| `-m` | Create home directory |
| `-s /bin/bash` | Normal (non-privileged) shell |
| `-e 2026-10-24` | **Absolute account expiry date** — login dies automatically on this date |

**Step 2 — Set a temporary default password:**
```bash
echo "donald_duck:TempPassword123!" | sudo chpasswd
```
`chpasswd` reads `username:password` pairs from **standard input** and sets them — ideal for scripted onboarding.

> ⚠️ **Security note (📌 Supplement — improvement over the PDF):** `echo` with a plaintext password puts it in your **shell history** (`~/.bash_history`) and process list. Safer alternatives:
> ```bash
> # Interactive (no history exposure):
> sudo passwd donald_duck
> # Or prevent history recording:
> history -d $((HISTCMD-1))
> ```
> The PDF's command *works*; just be aware of the exposure in real environments. *(Source: [chpasswd(8)](https://man7.org/linux/man-pages/man8/chpasswd.8.html))*

**Step 3 — Force immediate password expiration to trigger change on first login:**
```bash
sudo passwd -e donald_duck
```
Now the very first login demands a password change — the temporary password is used exactly once.

**Step 4 — Assign user to the system audit group:**
```bash
sudo groupadd -f audit_team
sudo usermod -aG audit_team donald_duck
```
(`-f` = **force**: create the group if it doesn't exist, succeed silently if it does — good practice in reusable scripts.)

**Step 5 — Verify expiration rules for the newly created auditor account:**
```bash
sudo chage -l donald_duck
```
**Expected output (typical):**
```
Last password change                                    : ...
Password expires                                        : ...
Password inactive                                       : never
Account expires                                         : Oct 24 2026     ← from -e
Minimum number of days between password change          : 0
Maximum number of days between password change          : 99999
Number of days of warning before password expires       : 7
```
Check that **"Account expires"** shows your `-e` date. ✔

#### Requirement → Mechanism Mapping (great exam summary)

| Requirement | Mechanism Used |
|---|---|
| Expires in 30 days | `useradd -e DATE` (absolute expiry) |
| Restricted privileges | Regular account (no sudo groups), only `audit_team` membership |
| Forced password change at first login | `chpasswd` + `passwd -e` |

> 📌 **Supplement:** For a strictly relative "30 days from today" expiry, compute the date, e.g. `sudo chage -E $(date -d "+30 days" +%Y-%m-%d) donald_duck`. *(Source: [chage(1)](https://man7.org/linux/man-pages/man1/chage.1.html))*

## 7. Administration Best Practices Checklist

*(From the PDF page 8 — with one disclosed gap filled.)*

| # | Practice | Explanation |
|---|---|---|
| 1 | **Principle of Least Privilege (PoLP)** | Avoid logging in directly as root. Grant standard user accounts administrative rights selectively using `/etc/sudoers` or `/etc/sudoers.d/`. |
| 2 | **Disable Unused Shells** | Set the login shell for system services to `/usr/sbin/nologin` or `/bin/false`. |
| 3 | **Periodic Auditing** | Periodically run checks for accounts missing passwords, unauthorized UIDs of `0`, or orphaned files. |
| 4 | **Umask Management** | Configure default file creation permissions (`umask 027` or `077`) in `/etc/profile` or `/etc/bashrc` to ensure restrictive permissions by default across all created user files. |

> 🔧 **PDF gap disclosed:** The *Periodic Auditing* bullet in the source ends with a colon but lists no commands. 📌 **Supplement — here are the audit commands it refers to** (all safe, read-only):
> ```bash
> # Accounts with no password / locked password entries
> sudo awk -F: '($2 == "" || $2 == "!") {print $1}' /etc/shadow
>
> # Any account other than root whose UID is 0 (red flag!)
> sudo awk -F: '($3 == 0 && $1 != "root")' /etc/passwd
>
> # Orphaned files (owned by a UID/GID with no account)
> sudo find / -nouser -o -nogroup 2>/dev/null
>
> # Accounts with usable shells (review this list)
> grep -vE '(nologin|false)$' /etc/passwd
> ```
> *(Sources: [shadow(5)](https://man7.org/linux/man-pages/man5/shadow.5.html), [find(1)](https://man7.org/linux/man-pages/man1/find.1.html))*

## 9. Exam Preparation

### 9.1 Important Definitions

- **Multi-user OS:** Linux isolates resources, manages system access, and enforces security policies; every process and file is tied to a user and group.
- **Primary group:** The single group assigned at user creation; new files are owned by it by default.
- **Secondary (supplementary) groups:** Optional extra groups granting additional privileges (e.g., `docker`, `sudo`, `wheel`).
- **`useradd` vs. `adduser`:** `useradd` = low-level universal utility; `adduser` = friendly interactive Perl script on Debian/Ubuntu.
- **`/etc/gshadow`:** Root-only file holding group passwords and administrative group overrides.
- **SetGID on a directory:** New files created inside inherit the directory's group ownership.

### 9.2 Key Concepts & Facts

- UID tiers: root `0`, system `1–999`, regular `1000+`.
- `usermod -aG` — the `-a` prevents **replacing** existing supplementary groups.
- `usermod -L/-U` locks/unlocks by prepending/removing `!` on the hash in `/etc/shadow`.
- `passwd -e` expires the password → forced change at next login.
- `chage` flags: `-M` max age, `-m` min age, `-W` warn, `-E` absolute expiry, `-l` list.
- `userdel -r` removes home directory **and mail spool**; other owned files become **orphaned**.
- `groupadd -r` → system GID; `groupmod -n` rename; `groupmod -g` re-GID.
- `gpasswd -a/-d/-A` = add member / delete member / assign group admin (admins manage membership **without root**; recorded in `/etc/gshadow`).
- Directory modes: `770` = private department share; `2770` = shared dir with group inheritance (`s` in `ls -l` output).
- `chpasswd` reads `user:pass` from stdin; `groupadd -f` won't fail if the group exists.

### 9.6 Common Mistakes

| Mistake | Correction |
|---|---|
| `usermod -G grp user` to "add" a group | Missing `-a` → **replaces** all secondary groups |
| `useradd newuser` and expecting a home dir | Add `-m` explicitly |
| Deleting a group that is a user's primary group | `groupdel` refuses — change the user's primary group first |
| Forgetting `passwd user` after `useradd` | New accounts have no password → effectively locked |
| Using `770` where group inheritance is needed | Use `2770` (SGID) so new files get the team group |
| Pasting plaintext password via `echo ... \| chpasswd` | Ends up in shell history — use `passwd` interactively |
| Changing a GID and assuming files follow | Files keep the numeric GID → re-`chgrp` affected trees |
| Assuming group membership applies instantly | Running sessions need re-login (or `newgrp`) |
