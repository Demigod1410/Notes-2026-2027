1. Introduction

In Unix-like operating systems, commands process information using data channels known as standard streams. By default:

     Commands receive input from your keyboard,
     Commands display regular output on the terminal screen,
     Commands send error messages to the same screen.

Understanding I/O Redirection and Piping allows you to alter these default behaviors, enabling data flow between commands, files, and processes to automate complex tasks seamlessly.

     

    Analogy: Think of each command as a small factory machine. Standard streams are its conveyor belts: one belt brings raw material in (stdin), one sends finished products out (stdout), and one carries rejected/broken items out (stderr). Redirection simply re-points the belts — send the output belt into a warehouse (file), into another machine (pipe), or off a cliff (/dev/null).

2. Understanding Standard Data Streams
2.1 Simple Definition

Every command executed in the Linux shell is assigned three standard I/O channels. Each channel is represented by an integer called a File Descriptor (FD).
2.2 The Three Streams (from the PDF — complete table, pages 1–2)
Stream Name
	
File Descriptor
	
Default Source / Destination
	
Description
Standard Input (stdin)	0	Keyboard	The stream from which a command reads its input data.
Standard Output (stdout)	1	Terminal Screen	The stream where a command sends its normal, non-error output.
Standard Error (stderr)	2	Terminal Screen	The stream reserved specifically for error messages and diagnostics.

2.4 Internal Working — What Is a File Descriptor Really?

(📌 Supplement — added for understanding; not in the PDF)

     A file descriptor is simply an integer index into the process's open-file table maintained by the kernel.
     By convention, every new process starts with FDs 0, 1, 2 already open and connected to the terminal.
     Redirection is just the shell re-pointing these FDs at a file (or another process's pipe) before the command runs — the command itself usually never knows the difference. This is why any command works with redirection, not just special ones.
     Why stderr is separate from stdout: so that normal results and error diagnostics can be routed independently — e.g., save results to a file while errors still flash on screen (see §3.3). (Source: Bash Reference Manual — Redirections)

2.5 Important Points

     ⭐ Memorize: stdin = 0, stdout = 1, stderr = 2. These numbers appear directly in redirection syntax (2>, 2>&1).
     Both stdout and stderr default to the same screen — but they are different streams, which is the entire reason separation tricks exist.
     stdin and stdout are buffered streams; stderr is typically unbuffered so errors appear immediately even if normal output is buffered. (📌 Supplement — bash man page)

3. Output Redirection (>, >>)

Output redirection changes where the standard output (stdout) or standard error (stderr) of a command is delivered — routing it away from the display screen and into a file.
3.1 Overwriting Output (>)

The > operator redirects stdout to a target file.

     If the target file exists → its contents are cleared (overwritten) before writing.
     If it does not exist → a new file is created.

Syntax:
bash
 
  
 
 
command > output_file
 
 
Example 1: Saving directory contents (from the PDF)
bash
 
  
 
 
ls -l /var/log > log_files.txt
 
 

Explanation: The ls -l /var/log command produces a detailed listing of files. Instead of displaying this output on the screen, the shell captures stdout and writes it into log_files.txt.
Example 2: Overwriting existing data (from the PDF)
bash
 
  
 
 
echo "Server Status: Active" > status.txt
 
 

Explanation: Writes "Server Status: Active" into status.txt. Any existing lines inside status.txt are completely replaced.

     

    ⚠️ Warning: > destroys existing file content with no undo and no confirmation. Accidentally running command > important_report.docx wipes that file. (📌 Supplement: set -o noclobber in bash can protect against accidental overwrites — bash(1))

3.2 Appending Output (>>)

The >> operator redirects stdout to a target file without overwriting existing data — it attaches the new output to the end of the file.

Syntax:
bash
 
  
 
 
command >> output_file
 
 
Example 1: Appending log entries (from the PDF)
bash
 
  
 
 
date >> system_activity.log
 
 

Explanation: Runs the date command and appends the timestamp to system_activity.log while preserving all prior entries.

     

    💡 Practical pattern: >> is the natural choice for logs and cumulative records (each run adds a line); > is for snapshots and reports (each run replaces the old content).

3.3 Redirecting Standard Error (2>, 2>>)

By default, > and >> only redirect stdout (stream 1). Error messages generated by stream 2 (stderr) will still appear on the screen unless explicitly redirected using file descriptor 2.
Example 1: Capturing permission errors separately (from the PDF)
bash
 
  
 
 
find /etc -name "*.conf" > config_files.txt 2> error.log
 
 

Explanation:

     stdout (found configurations) is saved into config_files.txt.
     stderr (e.g., "Permission denied" warnings — common when scanning /etc as a non-root user) is separated and recorded in error.log.

Visual of what happens:
text
 
  
 
 
find /etc ... ──stdout(FD 1)──▶ config_files.txt
              └─stderr(FD 2)──▶ error.log        (screen: nothing)
 
 
Example 2: Merging stdout and stderr into a single file (from the PDF)
bash
 
  
 
 
systemctl status nginx > service_status.txt 2>&1
 
 

Explanation: 2>&1 redirects stream 2 (stderr) to the same location as stream 1 (stdout), merging both outputs into service_status.txt.

     

    ⭐ Order matters — a classic exam trap: 2>&1 means "send stderr wherever stdout currently points." So > file 2>&1 works (stdout → file first, then stderr follows it), but 2>&1 > file does not merge (stderr is pointed at the old stdout = the screen, before stdout moves to the file). The PDF's example uses the correct order. (Source: Bash Reference Manual — Redirections)

     

    📌 Supplement: Modern bash also offers the shorthand &> file (equivalent to > file 2>&1), and 2>> appends stderr like >> appends stdout.

Example 3: Discarding unwanted output or errors (from the PDF)
bash
 
  
 
 
grep -r "main" /usr/include 2> /dev/null
 
 

Explanation: Writes all error messages directly to /dev/null — a special virtual device that discards all data written to it.

     

    Analogy: /dev/null is the system's trash chute — anything written to it vanishes without a trace.

    📌 Supplement: /dev/null also works for stdout (command > /dev/null). The idiomatic "silence everything" is command > /dev/null 2>&1. (Source: null(4))

4. Input Redirection (<, <<, <<<)

Input redirection feeds data into a command's stdin from a file or string rather than waiting for keyboard entry.
4.1 Standard Input Redirection (<)

Syntax:
bash
 
  
 
 
command < input_file
 
 
Example 1: Counting lines from a file stream (from the PDF)
bash
 
  
 
 
wc -l < inventory.csv
 
 

Explanation: The wc -l command counts the lines in inventory.csv. Unlike wc -l inventory.csv, using < causes wc to read from stdin, so the filename is not printed alongside the line count.

Why the output differs (understanding check):
Command
	
Input source
	
Output
wc -l inventory.csv	wc opens the file itself	42 inventory.csv (includes name)
wc -l < inventory.csv	shell opens the file, pipes it to stdin	42 (just the count)
 
 

     

    📌 Supplement: The shell does the opening — the command never even learns the filename. This is why < also works with commands that can't open files themselves, e.g., sort < unsorted.txt. (Source: wc(1))

4.2 Here-Document (<<)

A Here-Document (Here-Doc) allows passing a multi-line input block to a command directly within a script or command line, until a specified delimiter (often EOF) is encountered.
Example 1: Interactive file creation (from the PDF)
bash
 
  
 
 
cat << EOF > summary.txt
Project Name: Core Engine
Status: Production
Version: 2.4.0
EOF
 
 

Explanation: Passes all three lines directly to cat, which writes them into summary.txt until EOF is reached.

How it works, step by step:

    << EOF tells the shell: "collect input lines until you see a line containing exactly EOF".
    The shell feeds every collected line to cat's stdin.
    > summary.txt sends cat's stdout into the file.
    The terminator line EOF must appear at the start of its own line to end the block.

     

    💡 Tips (📌 Supplement):

         The delimiter word is arbitrary — END, STOP, anything — but it must match exactly.
         Quoting the delimiter (<< 'EOF') disables variable expansion inside the block — useful when writing scripts that generate other scripts. (Source: Bash Reference Manual)

4.3 Here-String (<<<)

Passes a single string variable or literal directly into standard input without spawning an external echo process.
Example 1: String processing (from the PDF)
bash
 
  
 
 
base64 <<< "LinuxSystem"
 
 

Explanation: Feeds "LinuxSystem" into the base64 tool via stdin.

Expected output (📌 Supplement — demonstration):
text
 
  
 
 
TGludXhTeXN0ZW0K
 
 

<< vs. <<< — quick contrast:
Operator
	
Feeds
	
Lines
	
Typical use
<< EOF	Multi-line block	Many	File creation, multi-line config in scripts
<<< "text"	One string	One	Quick single-value input (here-string)
 
 
5. Command Piping (|)
5.1 Simple Definition

Piping connects the standard output (stdout) of one command directly into the standard input (stdin) of another command. This creates an in-memory data processing line without creating intermediate disk files.
5.2 The PDF's Diagram (page 5 — reproduced faithfully)
text
 
  
 
 
+---------------+          +---------------+
|   Command A   | -- (stdout) -> | Command B |
+---------------+  [Pipe |]  +---------------+
 
 

Syntax:
bash
 
  
 
 
command1 | command2 | command3
 
 
5.3 Internal Working

(📌 Supplement — added for understanding)
  

stdout ──▶ pipe (kernel buffer) ──▶ stdin

stdout ──▶ stdin

Command A

Command B

Command C
 
 

     The kernel creates a pipe buffer in memory; both commands run simultaneously (concurrently), not one after the other.
     Data streams through as it's produced — no temp files, no waiting. This is the essence of the Unix philosophy: small tools composed into powerful pipelines.
     ⚠️ Key limitation: pipes carry stdout only — stderr does not travel down a pipe (unless explicitly merged with 2>&1).

5.4 Piping Examples
Example 1: Filtering process listings (from the PDF)
bash
 
  
 
 
ps aux | grep "python"
 
 

Explanation:

    ps aux outputs all active system processes.
    The pipe (|) sends that output directly to grep.
    grep "python" filters and displays only lines matching "python".

Example 2: Sorting and removing duplicate log entries (from the PDF)
bash
 
  
 
 
cat access.log | awk '{print $1}' | sort | uniq -c | sort -nr
 
 

Explanation (stage by stage):
Stage
	
Command
	
What it does
a	awk '{print $1}'	Extracts IP addresses (column 1) from each log line
b	sort	Sorts them alphabetically so duplicate IPs are adjacent
c	uniq -c	Eliminates adjacent duplicates and counts occurrences
d	sort -nr	Sorts the counts numerically in reverse order to show top visitors
 
 

     

    💡 Conceptual gems hidden here (likely exam points):

         uniq only collapses adjacent duplicates — which is exactly why sort must run before uniq.
         sort -n = numeric sort, -r = reverse (descending). -nr = biggest count first — the classic "top-N" pattern.

    (📌 Supplement: this pipeline is often simplified as awk '{print $1}' access.log | sort | uniq -c | sort -nr — the leading cat is optional since awk accepts a filename. See UUOC — Useless Use of Cat.)

5.5 Essential Pipe Utilities
Using tee (Dual Stream Output)

The tee utility reads standard input and writes it simultaneously to standard output and one or more target files.
bash
 
  
 
 
df -h | tee disk_usage.txt | grep "/dev/sda"
 
 

Explanation: Saves the complete output of df -h to disk_usage.txt while continuing to pass the output down the pipeline so grep can filter /dev/sda for terminal display.

     

    Analogy: tee is a T-junction on a water pipe — the flow continues downstream (to the next command) and a copy is diverted into a container (the file).

    📌 Supplement: Without tee, the grep would only see output after saving — with redirection (>), nothing continues down the pipe at all. Add -a to append instead of overwrite. (Source: tee(1))

Using xargs (Converting Stream to Arguments)

Some commands (e.g., rm, cp, kill) do not accept data via stdin and require arguments instead. xargs converts standard input into command-line arguments.
bash
 
  
 
 
find . -name "*.tmp" | xargs rm -f
 
 

Explanation: Finds files ending in .tmp and passes the file names as positional arguments to rm -f.

Why this is needed — the mental model:
text
 
  
 
 
WITHOUT xargs:  find → "file1.tmp\nfile2.tmp" ─stdin─▶ rm   ✘ (rm ignores stdin)
WITH xargs:     find → "file1.tmp\nfile2.tmp" ─▶ xargs ─▶ rm -f file1.tmp file2.tmp  ✔
 
 

     

    ⚠️ Warning (📌 Supplement): find | xargs rm is destructive. Spaces in filenames break naive xargs — the safe idiom is:
    bash
     
      
     
     
    find . -name "*.tmp" -print0 | xargs -0 rm -f
     
     

    Preview first with find . -name "*.tmp" | xargs ls -l before deleting. (Source: xargs(1))

6. Combining Piping and Redirection

Piping and redirection can be combined in a single command line. Data can flow through multiple pipeline filters before being saved to a file.
The Flow Pattern (from the PDF, page 7)
text
 
  
 
 
Input File (<) --> Command 1 --> Pipe (|) --> Command 2 --> Output File (>)
 
 
Example 1: Web Server Log Analysis (from the PDF)
bash
 
  
 
 
grep "HTTP/1.1 500" /var/log/nginx/access.log | awk '{print $7}' |
sort | uniq -c > internal_errors.txt
 
 

Explanation:

    Searches /var/log/nginx/access.log for lines containing Server Error status code 500.
    Extracts the requested URL path (column 7 — in the default nginx combined log format, field 7 is the request URI).
    Sorts the URIs and counts duplicate requests (sort | uniq -c).
    Saves the consolidated error summary into internal_errors.txt.

The full data journey (📌 Supplement — trace diagram):
text
 
  
 
 
 access.log ─▶ grep "500" ─▶ awk $7 ─▶ sort ─▶ uniq -c ─▶ internal_errors.txt
  (raw lines)  (error lines)  (URIs)  (grouped) (counted)   (final report)
 
 

     

    💡 Note the > at the very end only — redirection captures the output of the entire pipeline, not of individual stages. This combined filter-then-save pattern is one of the most common in real administration work (cron jobs, monitoring scripts, quick incident analysis).

9. Exam Preparation
9.1 Important Definitions

     Standard streams: The three default data channels (stdin, stdout, stderr) every shell command is assigned.
     File Descriptor (FD): The integer representing an I/O channel — 0, 1, 2 for stdin, stdout, stderr.
     Redirection: Changing where a stream is delivered — from terminal to file (or vice versa).
     Pipe (|): Connecting one command's stdout directly into another command's stdin — an in-memory processing line without intermediate disk files.
     Here-Document (<<): Passing a multi-line input block to a command until a delimiter (e.g., EOF) is encountered.
     Here-String (<<<): Passing a single string directly into stdin without an external echo process.
     /dev/null: A special virtual device that discards all data written to it.
     tee: Utility that writes stdin simultaneously to stdout and one or more files (dual stream output).
     xargs: Utility that converts standard input into command-line arguments for commands that don't read stdin.

9.2 Key Facts to Memorize
Fact
	
Value
FD numbers	stdin = 0, stdout = 1, stderr = 2
> behavior on existing files	Overwrites (clears first)
>> behavior	Appends, preserves existing content

Meaning of 2>&1	Send stderr to wherever stdout currently points

uniq requirement	Needs sorted input (duplicates must be adjacent)

9.6 Common Mistakes
Mistake
	
Correction
Thinking > also captures errors	> moves stdout only; errors still display — use 2> or 2>&1
Writing 2>&1 > file to merge	Wrong order — stderr points at the old stdout; use > file 2>&1
Using > for logs	Overwrites history — use >>
Running uniq on unsorted input	uniq only collapses adjacent duplicates — sort first
Piping into rm/cp/kill directly	These ignore stdin — insert xargs
Expecting stderr to flow through a pipe	Pipes carry stdout only; merge explicitly with 2>&1 if needed
xargs rm without preview	Destructive — check with ls first; handle spaces via `-print0
Confusing < with <<	< reads a file; << opens a typed multi-line block ending at a delimiter
