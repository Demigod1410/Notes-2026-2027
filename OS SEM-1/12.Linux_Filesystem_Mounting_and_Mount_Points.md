## 1. Core Concepts: Mounting and Mount Points

### 1.1 Simple Definition — The Big Picture

Unlike **Windows**, which assigns **drive letters** (such as `C:`, `D:`, or `E:`) to different storage partitions, **Unix-like operating systems organize all directories and files into a single hierarchical tree structure starting at the root directory (`/`)**.

> **Analogy:** Windows gives every new storage device its *own separate building* (C: building, D: building). Linux has **one single building** with one entrance (`/`) — mounting is the act of installing a new room **inside the existing building**, at a specific doorway (the mount point). You always navigate within the one building; you never "switch buildings."

### 1.2 Key Definitions (from the PDF — memorize verbatim)

- **Mounting:** The process by which the operating system **attaches a filesystem on a storage device** (such as a hard drive partition, USB drive, network share, or ISO file) **to a specific directory** in the system's unified directory tree.
- **Mount Point:** An **empty directory within the existing filesystem tree** that serves as the **access portal** to the newly attached storage device. Once a filesystem is mounted over a directory, any files or folders subsequently created **under that directory are written directly to the mounted storage device**.

### 1.3 Visual Model

*(📌 Supplement — diagram created for these notes)*

```
                      /  (root)
                      │
        ┌─────────────┼──────────────┐
      /home         /etc           /mnt
        │                           │
        │                        /storage   ◀── MOUNT POINT (empty dir)
        │                           ║
        │                    ┌──────╨───────┐
        │                    │  /dev/sdb1   │  ◀── physical device
        │                    │  (ext4)      │      attached by "mounting"
        │                    └──────────────┘
   everything above ── lives on the ROOT filesystem (e.g., /dev/sda1)
   everything below /mnt/storage ── lives on the MOUNTED device
```

### 1.4 Under the Hood: What Happens During Mount? (from the PDF)

When a mount operation executes, the **Virtual File System (VFS)** layer in the Linux kernel creates internal structures (such as **`struct mount`** and **`struct super_block`**). It sets specific **metadata flags on the mount point directory entry (dentry)**. This instructs **path lookup algorithms to pivot into the attached filesystem's root directory** whenever the mount point path is accessed.

**Explained simply (📌 Supplement):**

- **VFS** is the kernel's *translator layer* — it lets every application use the same system calls (`open`, `read`, `write`) regardless of whether the underlying filesystem is ext4, xfs, NFS, or a FAT USB stick.
- A **dentry** (*directory entry*) is the kernel's in-memory representation of a path component. Setting a flag on the mount-point dentry is how the kernel records: *"when resolving paths through this directory, jump into the other filesystem instead."*
- The **super_block** holds the metadata *of the mounted filesystem itself* (type, size, state).

**Important behavior — the "hidden files" effect (from the PDF):**

> If the directory chosen as a mount point **previously contained existing files, those files become temporarily invisible and inaccessible** while the filesystem remains mounted. **Unmounting** the device safely **restores access** to the original underlying directory contents.

> 💡 This is a favorite exam/troubleshooting question: *"I mounted a disk on /mnt/storage but my old files vanished!"* — They didn't vanish; they're **underneath** the mount, shadowed until you unmount. Best practice: **always use empty directories** as mount points.

## 2. Associated System Files

Linux relies on specific **configuration and status files** to track **active, available, and boot-time** filesystems.

### 2.1 `/etc/fstab` (Filesystem Table)

The `/etc/fstab` file is a **static system configuration file evaluated during boot**. It specifies **which storage devices should be mounted automatically, at which mount points, and with what permissions**.

> **Analogy:** `fstab` is the building's *permanent fixture list* — written once, consulted every morning (every boot) about which rooms to install. A manual `mount` command, by contrast, is a *temporary* setup that disappears at the next reboot.

#### The Six Fields of `/etc/fstab`

Each line in `/etc/fstab` consists of **six space-delimited fields** *(PDF typo "fields:t" corrected)*:

| # | Field | Meaning | Example Values |
|---|---|---|---|
| 1 | **file system** | The device identifier — device path, or preferably its **Universally Unique Identifier** | `/dev/sdb1` or `UUID=...` |
| 2 | **mount point** | The path to the directory where the filesystem will attach | `/mnt/storage` |
| 3 | **type** | The filesystem format | `ext4`, `xfs`, `vfat`, `ntfs`, `nfs` |
| 4 | **options** | Comma-separated list of mount behaviors | `defaults`, `ro`, `noexec`, `nofail` |
| 5 | **dump** | Used by the **legacy `dump` backup tool** | `1` = enable backup, `0` = disable |
| 6 | **pass** | Order in which **`fsck`** checks filesystems at boot | `1` = root `/`, `2` = other partitions, `0` = disable checking |

#### Sample fstab line (annotated — from the PDF's Example 2)

```
UUID=e4d2a1b3-7c89-4f56-9101-abcdef123456  /mnt/storage  ext4  defaults,nofail  0  2
└──────────── field 1: device ────────────┘ └─ f2: point ─┘ └f3┘ └──f4: options──┘ │  └ f6: pass
                                                                                   └ f5: dump
```

> 💡 **Why prefer UUIDs over `/dev/sdb1`?** (📌 Supplement) Device names like `sdb1` can **change between boots** (USB order, added disks, controller differences) — the same disk might become `sdc1`. A **UUID is burned into the filesystem at creation and never changes**, so fstab always finds the right device. *(Source: [fstab(5)](https://man7.org/linux/man-pages/man5/fstab.5.html))*

> ⚠️ **Warning:** A malformed `/etc/fstab` can make a system **fail to boot**. Always test with `sudo mount -a` after editing (see Example 2, §4.2).

### 2.2 `/proc/mounts`

Located in the `/proc` **virtual filesystem**, `/proc/mounts` is **dynamically updated by the Linux kernel**. It reflects the **exact real-time state of all currently mounted filesystems** on the system.

- **Static vs. dynamic (key contrast):** `/etc/fstab` = *what should be mounted* (a wish list); `/proc/mounts` = *what actually is mounted right now* (reality).
- 📌 **Supplement:** `/proc` files are generated on-the-fly by the kernel — they occupy no disk space. *(Source: [proc(5)](https://man7.org/linux/man-pages/man5/proc.5.html))*

### 2.3 `/etc/mtab`

Historically, `/etc/mtab` was a file **maintained by the `mount` and `umount` user-space utilities**. On **modern Linux distributions running `systemd`**, `/etc/mtab` is typically implemented as a **symbolic link pointing directly to `/proc/mounts`**.

> 💡 **Why the change?** (📌 Supplement) The old user-space mtab could drift out of sync with the kernel (e.g., after mounts done outside those tools). Linking it to `/proc/mounts` guarantees it always matches kernel reality. Check on your own system: `ls -l /etc/mtab`. *(Source: [mtab history, util-linux docs](https://man7.org/linux/man-pages/man5/fstab.5.html))*

### 2.4 `/proc/filesystems`

A system file that **lists all filesystem types currently supported by the running kernel or loaded kernel modules**.

**Use case:** before mounting with `-t`, check if the kernel can actually handle the type:
```bash
cat /proc/filesystems | grep -w xfs
```
*(Entries prefixed with `nodev` are virtual/pseudo filesystems like `proc`, `sysfs`, `tmpfs` — they aren't tied to physical devices.)* 📌 Supplement per [filesystems(5)](https://man7.org/linux/man-pages/man5/filesystems.5.html).

### 2.5 System-File Summary Table

| File | Nature | What It Tells You | When It's Written |
|---|---|---|---|
| `/etc/fstab` | **Static config** (you edit it) | What *should* mount at boot, where, with which options | Administrator edits |
| `/proc/mounts` | **Dynamic** (kernel-generated) | What **is** mounted right now | Continuously, by kernel |
| `/etc/mtab` | Symlink → `/proc/mounts` (modern) | Same as `/proc/mounts` | Via the symlink |
| `/proc/filesystems` | **Dynamic** (kernel-generated) | Which filesystem **types** the kernel supports | Continuously, by kernel |

## 3. Essential Tools and Commands

| Command | Primary Function | Example Usage |
|---|---|---|
| `lsblk` | Lists **block devices** in a visual tree format. | `lsblk -f` |
| `blkid` | Displays device attributes, **including UUIDs and filesystem types**. | `sudo blkid /dev/sdb1` |
| `mount` | **Mounts a filesystem** or views active mounts. | `sudo mount /dev/sdb1 /mnt/data` |
| `umount` | **Unmounts** an attached filesystem from its mount point. | `sudo umount /mnt/data` |
| `findmnt` | **Searches or lists mounted filesystems** in a detailed tree format. | `findmnt --real` |
| `mountpoint` | **Checks whether a specified directory is an active mount point.** | `mountpoint /mnt/data` |

**Command-by-command notes (📌 Supplement):**

- **`lsblk -f`** — the `-f` adds filesystem type, UUID, and mount point columns. The tree shows parent disk → partitions. *Always the first command when a new disk appears.* *(Source: [lsblk(8)](https://man7.org/linux/man-pages/man8/lsblk.8.html))*
- **`blkid`** — the go-to command for **harvesting UUIDs for fstab**. *(Source: [blkid(8)](https://man7.org/linux/man-pages/man8/blkid.8.html))*
- **`mount` with no arguments** — simply prints all current mounts (reads `/proc/mounts`). *(Source: [mount(8)](https://man7.org/linux/man-pages/man8/mount.8.html))*
- **`findmnt --real`** — filters out pseudo/virtual filesystems (like `proc`, `tmpfs`), showing only *real* device mounts — cleaner output than bare `mount`.
- **`mountpoint`** — exits with status 0 if the directory is a mount point, 1 if not — perfect for scripts:
  ```bash
  mountpoint -q /mnt/storage || sudo mount /dev/sdb1 /mnt/storage
  ```

**Expected outputs (📌 Supplement — demonstrations):**

```
$ lsblk -f
NAME   FSTYPE FSVER LABEL UUID                                 FSAVAIL MOUNTPOINT
sda
├─sda1 ext4   1.0         a1b2...                                20G    /
└─sda2 swap   1           c3d4...                                [SWAP]
sdb
└─sdb1 ext4   1.0         e4d2a1b3-7c89-4f56-9101-abcdef123456   98G
```

```
$ mountpoint /mnt/storage
/mnt/storage is a mount point      # exit code 0
$ mountpoint /home/gaurav
/home/gaurav is not a mount point  # exit code 1
```

## 4. Practical Step-by-Step Examples

### Example 1: Creating and Mounting a New Storage Volume (temporary)

To attach a new secondary storage disk (e.g., `/dev/sdb1`) to the filesystem tree:

**Step 1 — Identify the device and filesystem:**
```bash
lsblk
```
*Look for the new unmounted device (no `MOUNTPOINT` value) and confirm its partition, e.g., `sdb1`.*

**Step 2 — Create a target mount point directory:**
```bash
sudo mkdir -p /mnt/storage
```
*(`-p` creates parents as needed and won't fail if it already exists.)*

**Step 3 — Mount the partition:**
```bash
sudo mount -t ext4 /dev/sdb1 /mnt/storage
```

| Part | Meaning |
|---|---|
| `-t ext4` | Specify the **filesystem type** (optional if auto-detection works) |
| `/dev/sdb1` | The **source device** |
| `/mnt/storage` | The **mount point** (target directory) |

**Step 4 — Verify the mount:**
```bash
findmnt /mnt/storage
```
*Expected output:*
```
TARGET        SOURCE    FSTYPE OPTIONS
/mnt/storage  /dev/sdb1 ext4   rw,relatime
```

> ⚠️ **Important:** this mount is **temporary** — it disappears at reboot. For permanence, see Example 2.

---

### Example 2: Configuring Persistent Boot Mounts via `/etc/fstab`

To ensure a device **automatically remounts after a system reboot**:

**Step 1 — Obtain the UUID of the target partition:**
```bash
sudo blkid /dev/sdb1
```

*Output (from the PDF):*
```
/dev/sdb1: UUID="e4d2a1b3-7c89-4f56-9101-abcdef123456" TYPE="ext4"
```

**Step 2 — Edit `/etc/fstab` and append the configuration entry:**
```
UUID=e4d2a1b3-7c89-4f56-9101-abcdef123456 /mnt/storage ext4 defaults,nofail 0 2
```

*Field-by-field mapping:*

| Position | Value | Field |
|---|---|---|
| 1 | `UUID=e4d2a1b3-...` | file system (UUID — boot-order-proof) |
| 2 | `/mnt/storage` | mount point |
| 3 | `ext4` | type |
| 4 | `defaults,nofail` | options (`nofail` = boot continues even if the disk is missing) |
| 5 | `0` | dump (disabled) |
| 6 | `2` | pass (fsck checks it after root, which is `1`) |

**Step 3 — Test the configuration without rebooting:**
```bash
sudo mount -a
```

> **(From the PDF):** *If no error messages are returned, the fstab syntax is valid and safe for rebooting.*

- `mount -a` mounts **everything listed in fstab that isn't already mounted** — it runs the same logic boot does, so silent success = safe fstab.
- 📌 **Supplement (cited):** even safer on systemd systems: `sudo findmnt --verify` performs a static fstab sanity check without mounting. *(Source: [findmnt(8)](https://man7.org/linux/man-pages/man8/findmnt.8.html))*
- ⚠️ **Warning:** never reboot *before* testing fstab — an error in this file is one of the most common causes of boot failures/emergency mode.

### Example 3: Creating a Bind Mount

A **bind mount** exposes an **existing directory tree at a second directory location simultaneously**.

```bash
sudo mkdir -p /mnt/logs_mirror
sudo mount --bind /var/log /mnt/logs_mirror
```

**How it works (📌 Supplement):** no device is involved — the kernel simply makes the *same underlying directory* reachable via a second path. Reading `/mnt/logs_mirror/syslog` **is** reading `/var/log/syslog`. Changes through either path are immediately visible through the other.

> **Analogy:** a bind mount is a **second door into the same room** — not a copy.
>
> **Real-world uses:** giving a container/chroot access to host directories, exposing a service's data under a path the service expects, read-only views (add `-o ro`: `mount --bind -o ro /var/log /mnt/logs_mirror`). *(Source: [mount(8)](https://man7.org/linux/man-pages/man8/mount.8.html))*

---

### Example 4: Mounting an ISO Image (Loop Device)

To read contents directly from a **disk image file** without burning or extracting it *(PDF typo "an disk" corrected)*:

```bash
sudo mkdir -p /mnt/iso_image
sudo mount -o loop ubuntu-installer.iso /mnt/iso_image
```

| Part | Meaning |
|---|---|
| `-o loop` | Uses a **loop device** — a pseudo-device that presents a *regular file* (`ubuntu-installer.iso`) as if it were a **block device** |
| Result | The ISO's internal filesystem becomes browsable at `/mnt/iso_image` |

> **Analogy:** a loop device is a trick that makes the kernel treat a *file* as a *disk*. The ISO *is* a disk image; the loop device lets you plug it in virtually.
>
> 💡 The loop device allocation is often implicit — modern `mount ubuntu-installer.iso /mnt/iso_image` usually attaches a free loop device automatically. *(Source: [mount(8), losetup(8)](https://man7.org/linux/man-pages/man8/losetup.8.html))*

## 5. Common Mount Options Reference

*(From the PDF — complete table.)*

| Option | Description |
|---|---|
| **`defaults`** | Default settings: **`rw`, `suid`, `dev`, `exec`, `auto`, `nouser`, and `async`**. |
| **`ro`** | Mounts the filesystem as **read-only**. |
| **`rw`** | Mounts the filesystem with **read-write** access. |
| **`noexec`** | **Blocks execution of binary executables** on the mounted filesystem (**enhances security**). |
| **`nosuid`** | **Disallows the operation of `set-user-identifier` or `set-group-identifier` bits** (see PDF 01, §10 — SUID/SGID are ignored on this filesystem). |
| **`nofail`** | Allows the **system boot process to continue** even if the device **fails to mount**. |
| **`user`** | Permits **unprivileged users to mount and unmount** the filesystem. |

**Security-in-practice notes (📌 Supplement):**

- A common hardening pattern for removable/external media:
  ```
  UUID=...  /mnt/usb  vfat  defaults,noexec,nosuid,nodev  0  0
  ```
  — even if malware lands on the USB stick, its binaries can't execute, can't abuse SUID, and can't pretend to be device nodes. *(Source: [mount(8)](https://man7.org/linux/man-pages/man8/mount.8.html))*
- **`user` implies** `noexec,nosuid,nodev` by default unless overridden — a fact worth knowing for exams.
- **`async` vs. `sync`:** `async` (default) means writes are cached and flushed later — faster, but data may be lost on sudden removal; this is why you **always unmount before unplugging** a USB drive.

## 6. Troubleshooting Mount Issues

### Resolving "Device is Busy" Errors

When attempting to unmount a filesystem, you may encounter an error indicating the target is busy:

```
umount: /mnt/storage: target is busy
```

**Why it happens (📌 Supplement):** some process is *using* the filesystem — an open file, a running program launched from it, or even **your own shell whose current working directory is inside the mount** (`cd` elsewhere first — the most common trivial cause!). *(Source: [umount(8)](https://man7.org/linux/man-pages/man8/umount.8.html))*

#### Step 1 — Identify processes holding open file handles on the mount point:

```bash
sudo fuser -mv /mnt/storage
```

*Expected output:*
```
                     USER        PID ACCESS COMMAND
/mnt/storage:        root     kernel mount /mnt/storage
                     gaurav    12345 ..c.. bash
```

**or:**

```bash
sudo lsof +D /mnt/storage
```

| Tool | Approach |
|---|---|
| `fuser -mv` | Lists **PIDs using the filesystem** (`-m` = by mount, `-v` = verbose) |
| `lsof +D` | Lists **every open file** under the directory tree (more detail, slower on big trees) |

#### Step 2 — Safely stop the conflicting processes, or perform a lazy unmount:

```bash
sudo umount -l /mnt/storage
```

**(From the PDF):** *Lazy unmounting detaches the filesystem immediately from the tree and cleans up references once active processes finish operations.*

**`-l` explained (📌 Supplement):** the mount point disappears from the tree **at once** (new accesses can't reach it), but processes that already have files open keep working until they finish — the filesystem is cleaned up when the last reference closes. *(Source: [umount(8)](https://man7.org/linux/man-pages/man8/umount.8.html))*

> ⚠️ **Caution:** prefer the *safe* route (find and stop the process) for production systems — lazy unmount means the device may genuinely never be safe to remove while those processes live.

## 7. Comparison Tables

### 7.1 Windows Drive Letters vs. Linux Mount Points (from the PDF's core idea)

| Feature | Windows | Linux |
|---|---|---|
| Namespace | **Multiple** trees: `C:\`, `D:\`, `E:\` | **Single** tree rooted at `/` |
| New storage appears as | A new drive letter | Contents **inside** an existing directory |
| Persistence | Automatic via drive letters | Requires `/etc/fstab` entry (or automounter) |
| Path example | `D:\data\file.txt` | `/mnt/storage/data/file.txt` |

### 7.2 Static vs. Dynamic Mount Information Files

| File | Static/Dynamic | Role |
|---|---|---|
| `/etc/fstab` | Static (admin-edited) | Boot-time mount *plan* |
| `/proc/mounts` | Dynamic (kernel) | Live mount *reality* |
| `/etc/mtab` | Symlink to `/proc/mounts` today | Legacy compatibility name |
| `/proc/filesystems` | Dynamic (kernel) | Supported filesystem *types* |

### 7.3 Temporary `mount` vs. Persistent `fstab` Entry

| Feature | `sudo mount ...` (command) | `/etc/fstab` entry |
|---|---|---|
| Survives reboot | ❌ No | ✔ Yes |
| Best for | Quick tests, removable media, one-off ISOs | Servers, fixed disks, NAS shares |
| Configured by | Command line | File edit + `mount -a` test |

### 7.4 Bind Mount vs. Copy vs. Symlink

| Feature | Bind mount | Copy (`cp -r`) | Symlink (`ln -s`) |
|---|---|---|---|
| Same data, second path | ✔ (live, same inode space) | ❌ (separate duplicate) | ✔ (path alias) |
| Survives original path move/rename | ✔ | ✔ | ❌ (breaks) |
| Works across the tree for dirs | ✔ | ✔ | ✔ |
| Typical use | Containers, chroots, read-only mirrors | Backups, duplication | Convenience shortcuts |

### 7.5 `umount` vs. `umount -l` (lazy)

| Feature | `umount` | `umount -l` |
|---|---|---|
| Requires no open files | ✔ (fails if busy) | ❌ (succeeds anyway) |
| Mount point removed from tree | Immediately | **Immediately** |
| Open files keep working | N/A | ✔ until processes finish |
| Safe default? | **✔ Yes** | Use when you know why it's busy |

## 8. Exam Preparation

### 8.1 Important Definitions

- **Mounting:** Attaching a filesystem on a storage device (partition, USB, network share, ISO) to a specific directory in the unified directory tree.
- **Mount point:** An (ideally empty) directory serving as the access portal to the mounted device; files created under it are written to the mounted device.
- **VFS (Virtual File System):** Kernel layer that provides a uniform interface over different filesystem types; creates `struct mount`/`struct super_block` and flags the mount-point dentry during mount.
- **Shadowed files:** Files pre-existing in a mount-point directory become invisible while the filesystem is mounted; unmounting restores them.
- **fstab:** Static boot-time configuration specifying what mounts where, with which options (6 fields).
- **Bind mount:** Exposing an existing directory tree at a second location simultaneously.
- **Loop device:** Pseudo-device presenting a regular file (e.g., ISO) as a block device.
- **Lazy unmount (`umount -l`):** Detaches the filesystem from the tree immediately; cleans up when active processes finish.

### 8.2 Key Facts to Memorize

| Fact | Value |
|---|---|
| fstab field count | **6** (device, mount point, type, options, dump, pass) |
| fsck pass order | `1` = root `/`, `2` = other, `0` = skip |
| dump field | Legacy `dump` tool: `1` enable / `0` disable |
| `defaults` expands to | `rw, suid, dev, exec, auto, nouser, async` |
| Kernel's live mount list | `/proc/mounts` (`/etc/mtab` → symlink to it) |
| Supported FS types list | `/proc/filesystems` |
| fstab safety test | `sudo mount -a` (silent = valid) |
| New-disk first command | `lsblk` (then `blkid` for UUID) |
| "Is this a mount point?" | `mountpoint /dir` (exit 0 = yes) |
| Real mounts only | `findmnt --real` |
| Busy-finder commands | `fuser -mv DIR` or `lsof +D DIR` |
| Why UUID over `/dev/sdb1` | Device names can change between boots; UUIDs are fixed |

### 8.5 Quick Revision Sheet ⚡

```
MODEL:     Windows = many trees (C:,D:) · Linux = ONE tree from /
           mounting = attach device FS at a directory (mount point)
KERNEL:    VFS creates struct mount + super_block · flags dentry
           · path lookup pivots into mounted FS root
           shadowing: pre-existing mount-point files hidden until unmount
FILES:     fstab (static plan, 6 fields) · /proc/mounts (live reality)
           /etc/mtab → symlink to /proc/mounts · /proc/filesystems (types)
FSTAB:     device | mountpoint | type | options | dump(0/1) | pass(1=root,2=other,0=off)
           prefer UUID= (device names can shift between boots)
TOOLS:     lsblk -f (tree+FS) · blkid (UUID) · mount/umount
           findmnt --real (real mounts) · mountpoint -q (test)
MOUNT:     sudo mount -t ext4 /dev/sdb1 /mnt/storage     (temporary)
PERSIST:   blkid → edit fstab → sudo mount -a (SILENT = SAFE) → reboot
SPECIAL:   bind:   mount --bind /var/log /mnt/mirror   (same dir, 2nd path)
           ISO:    mount -o loop file.iso /mnt/iso     (file-as-block-device)
OPTIONS:   defaults = rw,suid,dev,exec,auto,nouser,async
           ro/rw · noexec (no binaries) · nosuid (SUID/SGID ignored)
           nofail (boot continues) · user (unprivileged mount)
BUSY:      fuser -mv DIR | lsof +D DIR → stop proc → or umount -l (lazy)
```

### 8.6 Common Mistakes

| Mistake | Correction |
|---|---|
| Rebooting immediately after editing fstab | **Test first** with `sudo mount -a` — bad fstab = boot failure |
| Using `/dev/sdb1` in fstab | Fragile — device names can change; use `UUID=` |
| Mounting onto a non-empty directory | Works, but old files get **shadowed** (hidden until unmount) — use empty dirs |
| Confusing `/etc/fstab` (plan) with `/proc/mounts` (reality) | fstab = what *should* mount; `/proc/mounts` = what *is* mounted |
| Forgetting `nofail` on removable-media fstab entries | Without it, a missing USB disk can hang or break boot |
| Trying to unmount while your shell sits inside the mount | `cd` out first — your own CWD holds the mount busy |
| Using `umount -l` reflexively | Lazy unmount hides the real problem; find the process with `fuser`/`lsof` |
| Omitting `2` in pass for data partitions, or using `1` for them | `1` is reserved for root; data partitions get `2` |
| Writing `mount --bind` expecting a copy | Bind mount is *the same data at a second path* — not a duplicate |
